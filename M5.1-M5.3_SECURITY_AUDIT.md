# M5.1-M5.3 Security Audit

## 1. Executive Verdict

**FAIL — SECURITY BOUNDARY COMPROMISED**

The claims schema, canonicalization, HMAC, and normal minting path are well structured, but M5.3 can mint from a caller-created authorization because `AuthorizationResult._from_manager()` is publicly callable. This is a direct M4-to-M5 trust-boundary bypass.

## 2. Architecture Verdict

```text
M1 -> M2 -> M3 -> M4 -> M5
```

Normal path:

```text
M1 Plan
 ↓
M2 ValidatedIntentResult
 ↓
M3 CapabilityResolver
 ↓
M4 TaskAuthorizationManager
 ↓
M5.3 CapabilityMinter
 ↓
AuthenticatedCapability
```

The normal data flow is correct. However, the public M4 factory allows:

```text
Caller
 ↓
AuthorizationResult._from_manager(...)
 ↓
CapabilityMinter
 ↓
Authenticated capability
```

Therefore the M2/M4 trust boundary is bypassable.

## 3. M5.1 Audit

- **Schema correctness:** Mostly PASS.
- **Formal-model alignment:** PASS for agent, task, step, resource, operation, constraints, and expiry fields.
- **Immutability:** PASS for ordinary mutation and nested constraints.
- **Field completeness:** Good. Includes capability ID, task ID, step ID, agent, operation, resource, scope, constraints, timestamps, nonce, and usage policy.
- **Future verifier compatibility:** PASS structurally, provided M5.4 verifies the MAC before trusting deserialized objects.
- **Future lifecycle compatibility:** PASS. Lifecycle state is not mixed into immutable claims.

M5.1 correctly separates:

```text
Immutable authenticated claims
```

from:

```text
Mutable lifecycle state
```

## 4. M5.2 Audit

- **Canonicalization:** PASS.
- **Determinism:** PASS for sorted dictionaries, fixed fields, enum values, timestamps, UTF-8, and ordered lists.
- **HMAC:** PASS. Uses HMAC-SHA256.
- **Secret management:** PARTIAL. The key is excluded from claims and logs, but is supplied to `CapabilityMinter` by the caller.
- **Constant-time comparison:** PASS through `hmac.compare_digest`.
- **Authenticated fields:** PASS. Scope, resource, operation, constraints, task, step, expiry, nonce, agent, and usage policy are included.
- **Serialization:** PASS for canonical claim serialization.
- **Tampering resistance:** PASS when verification is performed through `verify_mac()`.

M5.2 does not provide full capability verification, which is correctly deferred to M5.4.

## 5. M5.3 Audit

- **Trusted authorization input:** FAIL.
- **ALLOW enforcement:** PASS for normal inputs.
- **Task binding:** PASS when using genuine M4 results.
- **Step binding:** PASS when using genuine M4 results.
- **Agent binding:** PASS through M3 resolution.
- **Resource binding:** PASS through M4 scope and exact step resource checks.
- **Operation binding:** PASS through M3 resolution and claims validation.
- **Constraint binding:** PASS. Constraints derive from M3 parameters.
- **Expiry:** PASS structurally. M5 controls a bounded five-minute default and one-hour maximum.
- **Nonce:** PASS. Uses `secrets.token_urlsafe(24)`.
- **Capability ID:** PARTIAL. The ID is the M3 template ID, not a fresh per-mint identifier. Freshness comes from the nonce.
- **Claim derivation:** PASS for the normal path.
- **Authority expansion resistance:** PASS for normal manager-issued results, FAIL against forged `_from_manager()` results.
- **Immutability:** PASS against ordinary mutation and `model_copy(update=...)`.

## 9. Findings

### Finding ID: M5-001

- **Severity:** HIGH
- **Location:** `app/permissions/authorization.py`, `_from_manager()`
- **Problem:** The factory is publicly callable and does not require an unforgeable issuer capability.
- **Why it matters:** A caller can construct an integrity-valid `ALLOW` result.
- **Attack scenario:** A caller invokes `_from_manager(...)` with `decision=ALLOW`, `capability_id=file.read`, and a valid scope, then passes it to `CapabilityMinter`.
- **Paper requirement affected:** Authorization must precede capability creation and only the Permission Manager may authorize.
- **Recommended fix:** Make result issuance inaccessible to ordinary callers, or require a private issuer token controlled exclusively by `TaskAuthorizationManager`. Add a regression test proving direct factory use cannot mint.

### Finding ID: M5-002

- **Severity:** MEDIUM
- **Location:** `app/security/minting.py`, `CapabilityMinter.__init__`
- **Problem:** The HMAC key is supplied directly by the caller constructing the minter.
- **Why it matters:** Key ownership is not clearly isolated inside the M5 security layer. Different callers can instantiate minters with different keys.
- **Attack scenario:** A caller supplies an attacker-controlled key and creates capabilities unverifiable by the intended future verifier.
- **Paper requirement affected:** M5 should own cryptographic protection.
- **Recommended fix:** Introduce a trusted process-scoped key provider owned by M5. Do not expose the secret through public minting APIs.

### Finding ID: M5-003

- **Severity:** MEDIUM
- **Location:** `app/security/minting.py`, `CapabilityMintingPolicy`
- **Problem:** The minting policy is mutable after construction.
- **Why it matters:** A caller can modify `lifetime` or `usage_policy` after the policy is created, changing future authority semantics.
- **Attack scenario:** Set `minter.policy.lifetime` to several days or change `usage_policy` from `ONE_TIME` to `REPEATABLE`.
- **Paper requirement affected:** Expiry and usage semantics must be developer-controlled.
- **Recommended fix:** Make the policy immutable and ensure all changes require trusted configuration replacement.

### Finding ID: M5-004

- **Severity:** MEDIUM
- **Location:** `app/intent/schemas.py`, `ValidatedIntentResult._from_validator()`
- **Problem:** The issuer marker is module-level and importable by callers.
- **Why it matters:** Python’s module privacy convention does not prevent an attacker from importing `_M2_ISSUER` and creating a validation artifact.
- **Attack scenario:** Import `_M2_ISSUER`, call `_from_validator()`, and create a valid-looking M2 artifact.
- **Paper requirement affected:** M2 validation must not be caller-forgeable.
- **Recommended fix:** Move artifact issuance into a controlled M2-owned factory or use an opaque capability object that is not exposed through a public classmethod.

### Finding ID: M5-005

- **Severity:** MEDIUM
- **Location:** `app/permissions/evaluator.py`
- **Problem:** M4.2 compares scope type, kind, and selector, but not `scope.resource_id`.
- **Why it matters:** Direct M4.2 calls can authorize different resource IDs if the selector is identical.
- **Attack scenario:** Use a scope for `secret.pdf` with the same selector as the policy for `report.pdf`.
- **Paper requirement affected:** Resource scope must remain bounded through M3 -> M4 -> M5.
- **Recommended fix:** Compare the exact authorized resource identity in M4.2, not only in M4.3.

### Finding ID: M5-006

- **Severity:** MEDIUM
- **Location:** `app/security/capabilities.py`, `AuthenticatedCapability`
- **Problem:** The authenticated wrapper accepts any correctly formatted 64-character MAC without verifying it.
- **Why it matters:** Deserialization alone does not establish authenticity.
- **Assessment:** Acceptable only because full verification is explicitly deferred to M5.4.
- **Recommended fix:** M5.4 must require `verify_mac()` before consuming any authenticated capability.

### Finding ID: M5-007

- **Severity:** INFO
- **Location:** M5.1/M5.3 capability identity design
- **Problem:** `capability_id` remains the M3 template ID, such as `file.read`, rather than a unique minted capability instance ID.
- **Why it matters:** Multiple minted capabilities share the same identifier.
- **Assessment:** The nonce provides per-mint uniqueness, but the field name may be ambiguous for replay tracking and auditing.
- **Recommended fix:** Decide in a later phase whether M5.3/M5.5 needs a separate instance identifier. Do not conflate it with the M3 template ID.

## 10. Positive Security Properties

- M5.1 claims are frozen.
- Nested constraints are recursively immutable.
- `model_copy(update=...)` retagging is rejected.
- Unknown capability IDs are rejected.
- Agent and operation must match M3 templates.
- Scope resource type must match the M3 capability.
- M5.2 signs a fixed, complete claim projection.
- Dictionary ordering is deterministic.
- Datetimes normalize to UTC.
- Unicode serialization is deterministic and UTF-8.
- Ordered lists preserve order.
- HMAC-SHA256 is correctly used.
- MAC comparison uses `hmac.compare_digest`.
- Secrets are excluded from serialized capability data.
- M5.3 refuses `DENY`.
- M5.3 rejects normal forged `AuthorizationResult` objects.
- Task, step, resource, operation, and agent substitutions are tested.
- Nonces use `secrets.token_urlsafe`.
- Expiry is bounded and M5-controlled in the normal path.
- No filesystem, desktop, browser, email, subprocess, or agent execution exists.
- Replay and lifecycle state are correctly deferred.

## 11. Missing Security Tests

### M5.1

- Attempt to mutate `PermissionScope` nested inside claims.
- Deserialize altered claims and ensure they are not treated as authenticated.
- Test mutation through `model_dump()` reconstruction.
- Test constraints containing all supported JSON scalar types.

### M5.2

- Explicit canonicalization of `-0.0`, large integers, and floating-point values.
- Unicode normalization policy, especially NFC versus NFD.
- Exact MAC test vectors with independently computed expected values.
- Verify every individual field, including usage policy and `scope.resource_id`, changes the MAC.

### M5.3

- Direct `_from_manager()` forgery must fail.
- Direct `_M2_ISSUER` import and artifact forgery must fail.
- Mutating `CapabilityMintingPolicy` after construction must fail or have no effect.
- Passing a caller-controlled HMAC key must be rejected by the public API.
- Deserialized `AuthorizationResult` must not mint.
- Deserialized `AuthenticatedCapability` must require M5.4 verification.
- Policy mutation after minter construction must not alter minted authority.
- Constraint substitution must be tested independently from parameter substitution.

### Future M5.4

- MAC verification before any claim use.
- Tampered serialized capability rejection.
- Wrong key rejection.
- Task/step/agent/resource/operation enforcement.
- Expiry enforcement.
- Invalid MAC format rejection.
- Deserialization trust boundary.

### Future M5.5

- Atomic `verify_and_consume()`.
- One-time replay rejection.
- Repeatable bounded usage.
- Expired state.
- Revocation/completion.
- Concurrent consumption race tests.

## 13. M5.4 Readiness

**Is M5.1-M5.3 structurally ready for M5.4?**

`NO`

What must change before M5.4:

- Close the public `_from_manager()` authorization forgery path.
- Establish a genuine M5-owned key-management boundary.
- Make minting policy immutable.
- Add exact resource-ID comparison in M4.2.
- Ensure M5.4 never trusts deserialized Pydantic objects without MAC verification.
- Clarify whether `capability_id` is a template ID or minted-instance ID.

## 14. M5.5 Readiness

**Is M5.1-M5.3 structurally ready for M5.5?**

`YES, WITH CAVEATS`

The claims contain task ID, step ID, nonce, expiry, and usage policy, and lifecycle state is correctly excluded from signed claims. Before implementation, M5.5 should define an atomic `verify_and_consume()` boundary and decide whether a separate capability-instance ID is required.

## 15. M6 Readiness

**Can M6 eventually consume capabilities without receiving authority to mint or broaden capabilities?**

`YES`

M6 can receive `AuthenticatedCapability` without receiving the HMAC secret, M4 policies, M3 registry, or minting authority. This depends on M5.4 enforcing MAC, task, step, agent, resource, operation, constraints, and expiry before execution.

## 16. Research Defensibility

`YES, WITH CAVEATS`

The implementation faithfully represents the paper’s staged design: developer-authored templates, deterministic authorization, task/step-bound claims, HMAC authentication, and deferred lifecycle enforcement. A strong reviewer would reject an unconditional security claim until the public M4 factory bypass and key/policy ownership issues are fixed.

## 17. Final Recommendation

`B — Fix M5.1-M5.3 first`

## Audit Scope and Verification

This was a read-only audit. No source files or tests were modified.

The complete test suite was executed:

```text
210 passed in 7.06s
```

Additional probes confirmed:

- Genuine M4 authorization can mint and produces a valid MAC.
- Deserialized authorization results lose the private integrity marker.
- Public `AuthorizationResult._from_manager()` can create an integrity-valid forged `ALLOW`.
- A forged manager result can mint `file.read` authority.
- Altering claims while retaining the old MAC fails cryptographic verification.
- Secrets are absent from serialized capability data.
- `CapabilityMintingPolicy` can currently be mutated after construction.
- No repository changes were made during the audit.
